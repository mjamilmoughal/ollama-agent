Notes from building this project — architecture, not a tutorial

How This Agent Is Built

A terminal chat agent that runs entirely against local Ollama models: a LangGraph loop underneath, twelve tools it can reach for, and a rendering layer that had to be rebuilt more than once before it stopped lying about what was on screen.

DRAFT — internal architecture notes for this repository (ollama-agent).

This is the same codebase used in the "six local models, one agent" experiments — but this piece isn't about what the models did. It's about how the thing they're running inside actually works: the graph that drives tool calls, the tools themselves, and the terminal UI that has to render a live-streaming, occasionally tool-calling, occasionally reasoning conversation without corrupting its own scrollback.

The core loop

The whole agent is one small langgraph StateGraph with two nodes:

START ──▶ chat ──▶ tools_condition │ │ │ no tool calls ──▶ END │ │ │ tool calls ──▶ tools ──▶ chat (loop)

chat invokes whichever Ollama model is currently selected via ChatOllama(model=model_name, reasoning=...).bind_tools(ALL_TOOLS), prefixed with a single long system prompt describing all twelve tools and the rules for using them. tools is a stock LangGraph ToolNode built from the same tool list. tools_condition is the routing function: if the model's response carries tool calls, go run them and loop back to chat; if not, the turn is done. A MemorySaver checkpointer holds the conversation, so switching models mid-session or clearing history is just swapping which checkpointer the graph is compiled against.

def build_app(model_name, checkpointer):
    reasoning = True if model_supports_thinking(model_name) else None
    llm = ChatOllama(model=model_name, reasoning=reasoning).bind_tools(ALL_TOOLS)

    def chat_node(state):
        response = llm.invoke([SystemMessage(content=SYSTEM_PROMPT), *state["messages"]])
        if not response.tool_calls:
            fake_call = parse_fake_tool_call(response.content)
            if fake_call:
                response = response.model_copy(update={"content": "", "tool_calls": [...]})
        return {"messages": [response]}

    graph = StateGraph(MessagesState)
    graph.add_node("chat", chat_node)
    graph.add_node("tools", ToolNode(ALL_TOOLS))
    graph.add_edge(START, "chat")
    graph.add_conditional_edges("chat", tools_condition)
    graph.add_edge("tools", "chat")
    return graph.compile(checkpointer=checkpointer)

That parse_fake_tool_call line matters more than it looks. Not every local model emits LangChain's native tool_calls structure reliably — some print a JSON object that looks like a tool call as plain text instead. Rather than silently treating that as a wrong answer, the chat node checks whether the model's own text parses as {"name": "...", "arguments": {...}} against a known tool name, and if so, promotes it into a real tool call before the graph routes on it. It's the difference between an agent that only works with models that support function-calling cleanly, and one that degrades gracefully on the ones that don't.

The tool belt

Twelve tools, grouped by what they're actually for:

GroupToolsWhat they do
Websearch_online, fetch_urlDuckDuckGo snippet search, then a full single-page read via trafilatura when the snippet isn't enough.
Site crawlingdiscover_site_pages, fetch_urlsrobots.txt + sitemap + same-site link discovery, bounded by depth/page/time limits; then a batched, query-focused multi-page read.
Filesystemfind_project_file, find_file, read_file, search_in_fileFuzzy name search (project-scoped vs. anywhere-on-disk with explicit user consent), paginated reading, and bounded in-file grep.
JSON analysisinspect_json, get_json_value, rank_json_records, highest_nested_json_countSchema-first, deterministic queries over a JSON file so the model never has to eyeball a large dataset or compute an aggregate from a snippet.

A few design choices repeat across all of them:

  • Shared engines, not copy-pasted logic. find_file and find_project_file both call into _file_search.py's search_tree/match_tier; every filesystem tool resolves relative paths against the same _project.py::PROJECT_ROOT. site_tools.py imports its rejection check directly from fetch_url.py instead of re-implementing it.
  • Everything is bounded. Max file size, max scan time, max entries walked, max crawl depth, max output characters — every tool caps its own blast radius and says so in its result ("...may be incomplete") rather than silently truncating and letting the model assume completeness.
  • SSRF-aware fetching. fetch_url's _rejection_reason() resolves the hostname and rejects private, loopback, link-local, and reserved IP ranges before ever opening a connection — so a model can't be tricked (by a redirect, or a page it read) into reaching internal network services. site_tools.py reuses the exact same check for crawling and batch fetching, so there's one place that decides what's fetchable, not three slightly different ones.
  • find_file needs a human in the loop; find_project_file doesn't. The system prompt is explicit: searching the whole filesystem requires the user to name a location first (home directory, a drive letter, a specific folder) — never a default to "everything." Searching inside the current project needs no such confirmation, since that's already the working set.

Why JSON gets its own tool family

The four JSON tools exist because "read the file and compute the answer" doesn't scale — a model asked "who scored the most goals" over a 9,000-line tournament dataset either burns most of its context window on raw JSON or just guesses. inspect_json walks the structure breadth-first and reports paths, types, and array shapes without ever returning the data itself; the model is expected to call it first on anything unfamiliar, then use the exact field names it discovers in the follow-up calls. rank_json_records and highest_nested_json_count both return every tied record at the maximum, not just one — ties are a real failure mode for models that pick an arbitrary "first" result and report it as the answer.

Designing the terminal UI

The chat loop uses rich's Live displays for anything that updates in place: a spinner while waiting on the model, a bounded scrolling preview of the model's live reasoning trace once a thinking-capable model starts emitting one, and a bounded preview of the reply itself while it streams. "Bounded" is the operative word, and it's bounded on purpose, not by accident — the first version wasn't, and that turned into the most instructive bug in this codebase.

Reasoning display
Ollama streams `thinking` tokens separately from `content` for models that support it (checked once per model via `/api/show`'s `capabilities` list, since asking a non-thinking model for reasoning is a hard 400). While those tokens arrive, the terminal shows a small animated block — a spinner header plus only the last four wrapped lines of the trace so far — that collapses into a single ✻ Thought for 12.3s line the moment real content starts. The full trace is never dumped to the screen; only a rolling window of it.
Post-mortem: the unbounded Live region

The reply itself was originally streamed the same way ollama run shows it — printed raw as tokens arrived, then, once the model finished, the raw text was erased with a hand-rolled cursor-up N rows, clear-to-end-of-screen sequence and replaced with a properly rendered Markdown version. Two things went wrong with that, both traced by replaying real sessions through a headless terminal (pyte) with scrollback recording enabled, byte for byte:

  • The row count used to move the cursor was computed with Rich's own line-wrapping math, which doesn't always agree with how the real terminal wraps the same raw text — so a long reply could erase more (or less) than intended, corrupting whatever was printed above it. Long replies routinely exceeded the terminal's visible height entirely, which skipped the "clean" redraw path altogether and left the literal **bold** markdown syntax on screen, unrendered.
  • Deeper down: a single shared Live object was being stopped and restarted repeatedly across a turn — once after a thinking phase, again around every tool call. Rich's Live doesn't reset its internal "how tall was my last render" state across a stop-then-start on the same instance, so the very next redraw after a restart erased based on a stale height left over from whatever it had rendered before — a five-line thinking box, say — even though nothing five lines tall belonged there anymore. That erased real content: tool-call bullets, the "Thought for Xs" line, sometimes the user's own typed question, however far back the stale height reached.

The fix removed the hand-rolled cursor math entirely. Both the thinking trace and the streaming reply now render through bounded Live regions — a fixed handful of lines, always — while they're in motion, and the final, fully-rendered form is printed exactly once via a plain console.print() when they're done, with no cursor repositioning involved at all. And every restart of the shared spinner now constructs a brand-new Live instance instead of reusing a stopped one, so there's no stale render state left to go stale in the first place.

The practical rule that fell out of this: a live-updating terminal region is safe exactly as long as its maximum height is known in advance and small. The moment its height depends on how much content has streamed so far, it's one long reply away from needing more room than is physically left on screen — and no amount of careful cursor math survives a real terminal being forced to scroll mid-redraw.

Keeping the model honest

Local models — especially small ones — will confidently narrate having done things they didn't do. The system prompt pushes back on this directly: "Never say you searched, fetched, read, or analyzed a source unless a corresponding tool result is present in the conversation." Combined with the fake-tool-call promotion in chat_node, the aim is that a claim of tool use in the final answer should always correspond to a real entry in that turn's tool-call log — which matters, because that log is exactly what gets written out afterward for analysis.

Every turn is a data point

SessionLogger writes each turn to sessions/<timestamp>_<model>.json as it happens: the user message, the full reply, every LLM call's token counts and timing, every tool call's arguments/result/duration, and a chain of which calls were retries of earlier ones on the same tool. A few heuristics run automatically over that data — a turn with eight or more tool calls, or three identical calls in a row, gets auto-flagged as a possible infinite loop; text that looks like a failed tool call but never parsed gets flagged as malformed. None of that is treated as ground truth, though: /rate, /failure, /necessary//unnecessary, and /note let a human annotate the last turn directly from the terminal, and /task marks a boundary so turns can be grouped by what was actually being tested. That's the same log format the "six models" experiments were built on — this agent was designed to be measured, not just used.

None of this is exotic. It's a two-node graph, a bounded tool belt, and a rendering layer that took a real bug to get right. But that's roughly the point: the interesting failure modes in a local, tool-calling agent aren't in the model weights — they're in the seams between the model, the tools, and the terminal it's talking through.
