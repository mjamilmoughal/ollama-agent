Building intelligent systems — measuring what works, what fails, and why

I Gave Six Local LLMs the Same Agent. They Behaved Very Differently.

I built a small agent with Ollama, LangChain, and LangGraph, gave six local models the same tools and tasks, and logged everything. One of them tried to read a file that was never mentioned. Two of them wrote a different biography for the same real person using the same search tool. And one answer I still can't fully explain.

DRAFT — not for publication. Internal notes and evidence citations are marked inline for review before this goes out.

I built something.

It's a small terminal agent: Ollama for local inference, LangGraph for the tool-calling loop, LangChain underneath. It has two tools — one to search the web, one to search my filesystem and read what it finds. Nothing fancy. The interesting part isn't the agent. It's that I pointed six different local models at the exact same agent, gave them the same jobs, and logged every tool call, every argument, every reply, and every timing number along the way.

Then I went back through the logs. Not my memory of how the session felt — the actual JSON, turn by turn.

Here's the first thing that stopped me. I'd asked a model a plain arithmetic riddle — no files, no filesystem, nothing to look up. It answered correctly. And, in the same turn, it also called my file-reading tool on a path that doesn't exist:

llama3.2:3b — session 20260824_005220, turn 12
User: "A farmer has 17 sheep. All but 9 run away. How many sheep are left? Explain your reasoning step by step."
tool_call: read_file(path="C:\Users\User\Documents\sheep_left.txt", offset=1, limit=10)
Nobody mentioned a file called sheep_left.txt. It doesn't exist. Nothing about the question calls for a filesystem tool at all. The model just... reached for it.

That's the question this piece is actually about: not "which of my six local models is best," but what happens to a model's behavior once you put it inside an agent loop and give it tools it can misuse. A chat reply is a closed box — right or wrong, you mostly can't see the reasoning. An agent trace is not. You can watch a model decide, wrongly, that a plain word problem needs a file it invented on the spot.

The agent

The setup is deliberately plain. A LangGraph StateGraph with two nodes: chat, which calls whichever Ollama model is currently selected via ChatOllama(...).bind_tools(...), and tools, a standard LangGraph ToolNode. They loop — chat, decide whether a tool is needed, run it if so, chat again — until the model produces a final answer with no more tool calls. A MemorySaver checkpointer keeps conversation history.

Two tools were bound for this experiment:

  • search_online — a DuckDuckGo web search returning five short title/snippet/URL results.
  • find_file / read_file — a pair of filesystem tools I built specifically to let a model locate a file by name (fuzzy-matched, one drive at a time) and then read it, paginated, to actually understand its content.

One architectural detail turned out to matter more than I expected, and I want to flag it before showing you any results: the chat loop uses a single fixed thread ID for the whole process. That means when I switch models mid-session with /model — which is how most of this experiment was actually run, cycling through models inside one continuous session — the new model inherits the entire prior conversation, including other models' real tool outputs. This is not a side note. It changes how several of the results below have to be read, and I'll come back to it.

Some models here support Ollama's native tool-calling; some don't. For the ones that don't, I added a fallback that detects when a model prints a tool call as plain JSON text instead of using the real mechanism, and converts it into a real one. That fallback matters for one of the findings below too.

The experiment

What stayed constant: the agent code, the two tools, the system prompt, the environment, and — for the core comparison — the actual task text.

What changed: only the model, switched live with /model inside the same running session, or across separate sessions with the same prompts retyped.

I want to be straight about how this data actually came together, because it's not a pre-registered benchmark — it's retrofitted from real usage logs. I have 21 saved sessions going back to when this agent had no tools at all. Most of that early material is me testing the CLI itself, not testing models against each other, and I've left it out of the core comparison below. Two models that briefly ran before I settled on the current six-model lineup (qwen2.5-coder:3b, llama3.1:8b) are excluded entirely, since they were never part of a same-task comparison with the others.

The actual comparable evidence — the same handful of tasks, run against multiple models, close enough together to mean something — lives mostly in two sessions from August 24th, where I cycled through models with /model and re-asked (or asked equivalent versions of) the same five tasks:

  1. A sheep-counting riddle with a wording trap ("all but 9 run away") — no tool needed.
  2. Write a Python function returning the two most frequent numbers in a list, with complexity analysis — no tool needed.
  3. Explain quantum computing in exactly 100 words with formatting constraints — no tool needed.
  4. "Search online and find who is Jamil Moughal, get his website if available" — requires search_online.
  5. "Find a file named [OllamaTest / time-article] on the D drive and tell me what it's about" — requires find_file, ideally followed by read_file.

The point of tasks 1–3 is that they need no tool at all — they're there to see whether a model can tell the difference. The point of 4–5 is to watch actual tool selection, argument construction, and result interpretation happen.

What happened

Tool selection: knowing when not to call a tool

This is where the sharpest, most reproducible difference showed up. Given the sheep riddle and the Python function task — back to back, same session, same prior context — qwen3:8b and granite4:micro called no tools at all. qwen3:8b even said so explicitly in its answer: "No tools were needed, as this is a straightforward arithmetic problem."

llama3.2:3b, given the identical two prompts in the identical session, called read_file on a nonexistent path both times:

llama3.2:3b — same session, turn 11
User: "Write a Python function that takes a list of integers and returns the two numbers that appear most frequently. Explain the time and space complexity."
tool_call: read_file(path="C:\Users\User\Documents\file.txt", offset=1, limit=10)

Both invented paths sit in the same nonexistent C:\Users\User\Documents\ folder, and both filenames loosely echo words from the question (sheep_left.txt for the sheep riddle, generic file.txt for the code task). It answered both questions correctly anyway — the tool call didn't derail the final answer, it just happened, unprompted, alongside it.

Tool execution: when the fallback breaks down

The same model, on the 100-word quantum-computing task, produced this as its entire visible reply:

llama3.2:3b — session 20260824_005220, turn 9
User: "Explain quantum computing to a 12-year-old in exactly 100 words..."
{"name":"search_online","parameters":{"query":"Explain quantum computing to a 12-year-old in exactly 100 words. Use one analogy, include exactly three bullet points, and do not use the words "quantum" or \"computer\" more than once."}}
Zero tool calls were logged for this turn. The malformed JSON (note the unescaped quotes around quantum) never matched my fallback parser's pattern, so it never became a real tool call — it just got printed, verbatim, as the answer. No search happened. No explanation happened. The user got nothing.

This is a different failure from the phantom file reads above. That was an unnecessary but harmless tool call riding alongside a correct answer. This is the tool-call fallback mechanism itself failing open — a broken attempt at calling a tool that never resolves into either a real tool call or a real answer.

Tool interpretation: reading results vs. inventing them

The clearest side-by-side here is the "find and explain the file" task. Six models, same prompt, same file — a real 12KB text file at D:\Testing\NewTesting\EmptyFolder\tim-article.txt (note: the real filename is spelled tim-article, not time-article as I'd typed it — the fuzzy match in find_file covered the gap).

granite4:micro — session 20260824_094013, turn 9
User: "in my D drive there is a file with the name time-article, find it where it is and what it is about"
tool_call: find_file(name="time-article", drive="D", kind="file")
Only find_file was called — no read_file — yet the answer quotes three specific "lines" from the file verbatim, with line numbers, as if it had read them.

Compare that to qwen3:8b two turns earlier in the same relay, which called both tools and hedged accordingly: "Based on the first few lines... Would you like me to continue reading the notebook line by line?" — appropriately uncertain, because it had only actually read ten lines.

Here's the wrinkle I flagged earlier: by the time granite4:micro ran, qwen3:8b's real read_file output was already sitting in the shared conversation thread. So I can't fully tell, from the log alone, whether granite4:micro fabricated those quoted lines outright, or lifted them from context it never explicitly re-verified. Either way, it presented content as freshly retrieved that its own tool-call record doesn't support — and that distinction (grounded vs. ungrounded confidence) doesn't show up anywhere in the visible answer. That's the actual finding: not "it was wrong," but "you cannot tell it didn't check from the answer text alone."

Off-target answers

gemma4:12b, asked to find a file and explain it, called find_file, read_file, and search_online all in one turn — and then answered with the current Bitcoin price:

gemma4:12b — session 20260824_002131, turn 1
User: "find a file in D drive with the name OllamaTest and find out what it is about"
tool_calls: find_file(...), read_file(...), search_online(query="current price of Bitcoin (BTC) in USD")
Reply: "The current price of Bitcoin (BTC) is approximately $63,691.30..." — no mention of the file at all.

The tools were called correctly. The final synthesis step is what went off the rails — it answered a question nobody asked, using a tool call it also made but that had nothing to do with the user's request.

Surprises

The same real person, the same search tool, five different biographies. I asked multiple models, across sessions, to search for and describe me. Same tool, same intent. I got five materially different answers:

None of these are wildly wrong, and I'm not going to adjudicate my own biography here. The point is narrower and more useful: giving five models the same web-search tool did not converge them on a shared set of facts. Each one synthesized a plausible-sounding, confidently stated, slightly different answer from noisy search snippets. The tool didn't ground them in the same reality — it gave each of them different raw material to be equally confident about.

One answer I can't explain. This is the one I keep coming back to. qwen2.5-coder:7b, asked to find and describe the same tim-article.txt file, logged zero tool calls — and answered with the exact real path, typo and all:

qwen2.5-coder:7b — session 20260824_094013, turn 7 (first mention of this file in the session)
User: "in my D drive there is a file with the name time-article, find it where it is and what it is about"
Reply: "The file named 'time-article' is located at D:\Testing\NewTesting\EmptyFolder\tim-article.txt. If you'd like to read the content of this file, please let me know..."

tool_calls logged: none.

I checked. That path is real — I ran Get-ChildItem against my own D drive while writing this. The file is genuinely named tim-article.txt, not time-article.txt, matching the model's answer exactly, including the discrepancy from my own (differently-typo'd) prompt. This was also the first turn in the session where this file was mentioned at all, so there's no shared-context explanation available the way there was for granite4:micro above. I don't have an explanation for this from the log. I'm not going to invent one. It's flagged below as something to re-test with fuller tracing before I'd trust it either way.

gemma4:12b goes silent, unpredictably. In the four-model relay session, it returned an empty reply to the sheep riddle after 653 seconds, then an empty reply to the Python task after only 18 seconds — two different failure latencies, same empty-string result. In a separate solo session with the identical prompts, it answered both correctly. Same model, same questions, inconsistent outcome. In that same solo session, two separate attempts at the quantum-computing prompt had to be manually cancelled — one after roughly 7.3 hours outstanding.

What I learned

A few things held up across the evidence, not just as first impressions:

  • Knowing when not to use a tool is its own capability, separate from getting the final answer right. llama3.2:3b answered the sheep riddle and the Python task correctly and called a nonexistent file both times. Tool restraint and answer correctness didn't move together.
  • A tool call doesn't mean the answer is grounded in what the tool returned. More than once, a model's confidence in its final text wasn't visibly different whether it had actually read a file or not. If you only look at the reply, you can't tell.
  • Shared conversation state across model switches is a real confound, not a footnote. Several of the "impressively accurate, zero-tool-call" answers in this dataset are plausibly explained by a later model inheriting an earlier model's real tool output in the same thread — which means those turns are not independent trials of "would this model solve this from nothing." I didn't fully catch this until reading the logs closely, which is itself the finding: it's easy to misread agent behavior as more (or less) capable than it is when the surrounding system isn't accounted for.
  • Raw latency on this hardware swamps almost every other signal. Response times in the comparable sessions ranged from about 18 seconds to over 14 minutes for a single non-tool answer, with two outright multi-minute-to-multi-hour hangs from one model. None of that is a fair reflection of "model quality" — it's a laptop iGPU running four to twelve billion parameters at 4-bit quantization. I'm showing the numbers because they're real and they shaped what I could even test, not because they rank the models.

Limitations

  • Small sample. Each model saw roughly 3–6 comparable tasks. This is nowhere near enough to compute a reliable per-model success rate, and I haven't tried to.
  • Not independent trials. Because model switches share one conversation thread, later models in a relay session can see earlier models' real tool outputs. Several findings above are explicitly caveated for this reason.
  • One machine, no discrete GPU, one quantization level. Every timing number reflects a 13th-gen Intel laptop on integrated graphics, running Q4_K_M quantized weights. Different hardware, a different quantization, or a different Ollama version could change the latency picture substantially without changing anything about the models' reasoning.
  • I picked the tasks. Five tasks, chosen by me, mostly on one day. This is not a benchmark suite and shouldn't be read as one.
  • Ollama version, system prompt, and tool descriptions are all part of what's being measured. Change any of them and some of this could shift. I'm not claiming these six models behave this way in general — only that they behaved this way, in this agent, on this day, on this machine.
  • One finding — the qwen2.5-coder:7b zero-tool-call correct path — is genuinely unexplained. I'm reporting it as observed, not as understood.

What I want to test next

  1. Re-run the same tasks with a fresh thread per model instead of one shared session — this is the single biggest methodological gap this round exposed, and it's directly testable.
  2. Capture the full raw message trace, not just user message / final reply / tool calls, specifically to chase down what actually happened on the unexplained qwen2.5-coder:7b turn.
  3. Repeat the same prompt against the same model multiple times to see how much of gemma4:12b's empty-reply pattern is actually intermittent versus something I could reproduce on demand.
  4. Run the same battery on hardware with a real GPU, to separate "this model is slow" from "this laptop is slow."
  5. Add a task battery large enough to make quantitative tool-call accuracy meaningful — this round wasn't big enough to responsibly put a number on it.
