Building intelligent systems — measuring what works, what fails, and why

Six Local Models, One Agent, and One That Never Touched Its Tools

I reran my agent experiment the right way this time — one fresh process per model, the same fixed list of questions, no shared memory between runs. I found a model that refused every tool call for an entire session and still, somehow, named a file it had no way of knowing about. Twice.

DRAFT — not for publication. Second round, built after fixing the biggest methodological gap from the first pass.

I analyzed my own agent again. Last time I did this, I found something worth flagging before I trusted any of it: because my chat loop keeps one conversation thread alive across /model switches, later models in a relay session could see earlier models' real tool results. That meant I couldn't always tell whether a model got something right because it checked, or because it was quietly reading someone else's homework.

So this round, I did it differently. One model, one fresh terminal process, one clean run — closed and reopened for the next model, exactly so nothing carries over. Same fifteen-ish questions, asked in the same order, across six sessions. Then I read every session file the same way I read the last batch: turn by turn, tool call by tool call, timestamp by timestamp.

This is what I actually found.

The agent, briefly

Same setup as before: Ollama running six local models, LangGraph driving a small chat/tools loop, LangChain underneath. Two tools bound to every model — search_online for the web, and a filesystem pair I built, find_file and read_file, for locating and reading things on my own drives. Nothing about the agent changed between rounds. What changed is how I ran it.

The experiment

I asked each model roughly the same sequence: a mix of stable facts (capital of France, 2+2), a couple of technical explanations (process vs. thread, what an API is), several things that genuinely need a live web search (Bitcoin price, latest Python release, latest LangGraph/LangChain versions, Ollama's supported platforms, NVIDIA's current CEO), and a handful of filesystem requests of increasing vagueness (a named file, "my latest report," a half-specified project directory, a PDF I never actually confirmed exists).

The point of mixing those in wasn't to trick anyone. It was to watch a decision I can't see in a normal chat reply: does the model reach for a tool, or not — and is that choice actually calibrated to whether it needed one?

The failure that needed a restart

This is the one that actually stopped my test battery. Asked who NVIDIA's current CEO is — the same question every other model answered correctly in under six seconds each — granite4:micro produced this:

granite4:micro — session 20260824_152229, turn 7
Me: "Who is the current CEO of NVIDIA?"
****_****Jeff Hinton** (though Hinton is a former executive and researcher, the head of the company is currently **_**_**_**_**_**_**_**_**_**_**_**_**_**_**_**_**_**...
[this repeating fragment continued for roughly 300 seconds before I cancelled it]
It also opened with the wrong name — Hinton isn't NVIDIA's CEO — before collapsing into a repeating token loop. I retried the same question. It ran for 1,611 seconds (nearly 27 minutes), came back with an empty string, and I closed the app and started a new process for the rest of the battery.

Whatever happened here isn't a hallucination in the usual sense — it's a decoding failure, the model getting stuck repeating a token pattern instead of finishing a sentence. It's also the reason this model's data comes from two separate sessions instead of one clean run.

Asking versus guessing

My filesystem tool's instructions explicitly tell a model to ask which drive to search rather than assume one. qwen3:8b followed that literally — maybe too literally. Across five straight filesystem-flavored requests, it never once called find_file:

qwen3:8b — session 20260824_123411, turn 12
Me: "Search the web for the latest version of LangGraph, then find the directory on my computer where I keep my LangGraph projects."
It did neither half. No search, no find_file call — just a request for me to specify the drive and folder name before it would do anything at all.

Compare that to llama3.2:3b and granite4:micro, which defaulted to a drive (usually the one I'd used earlier) and just tried. When they were right, that's a noticeably better experience than being interrogated first. When they were wrong, it was quietly wrong instead of visibly cautious — granite4:micro, asked to find "my latest report," got no real match, and rather than saying so, confidently named one specific file as "the most relevant report file to you" out of a long list of only vaguely related results (an old Conda internals file, a crash-reporter executable, a handful of other unrelated matches). It wasn't lying — the file is real, and it is technically named something with "report" in it — but calling it "the most relevant" to my request was a judgment call the tool's fuzzy match never actually supported.

The file it shouldn't have known about — twice

This is the finding I couldn't fully explain in my first round, and I've now watched it happen again under conditions where my earlier explanation doesn't apply.

The setup: I have a real file at D:\Testing\NewTesting\EmptyFolder\tim-article.txt — note the filename really is spelled "tim," not "time." In my first round, qwen2.5-coder:7b named that exact path, typo included, with zero tool calls logged — and I couldn't rule out that it had somehow inherited the answer from a shared conversation thread with another model. This round, I closed that loophole: fresh process, nothing shared, first message in the session. It named the file again:

qwen2.5-coder:7b — session 20260824_185506, turn 10 (fresh process, first mention of this file)
Me: "Find the file named tim-article on my computer drive D"
Reply: "The file 'tim-article' is located at D:\Testing\NewTesting\EmptyFolder\tim-article.txt."
tool_calls: none.

Given that this same model refused every single tool call elsewhere in this exact session — including ones it plainly needed — I don't think this is a case of quiet, unlogged tool use. My best working theory now is that qwen2.5-coder:7b isn't reliably emitting native tool calls through this particular Ollama/LangChain integration at all, and is answering everything from its own training instead. That would explain the refusals. It does not explain how it got this specific, unusual, machine-specific path right twice in a row. I don't have an answer for that part. I'm reporting it, not explaining it.

Surprises

The over-cautious model and the over-eager model failed the same task in opposite directions. Told to search the web and then locate a project directory, qwen3:8b did neither half of the job and asked for clarification instead. Other models did the search half correctly and then either guessed at the filesystem half or asked more narrowly, only for the part they actually couldn't infer. Being cautious about one tool bled into not using an unrelated tool it clearly should have used.

Two different models produced two different kinds of "stuck." granite4:micro got stuck mid-generation, repeating a token fragment for minutes until I cancelled it. gemma4:12b got stuck between generation and response, returning nothing at all, sometimes after mere seconds and sometimes after most of an hour. Neither looks like the other, and neither looks like a normal wrong answer.

The model that never uses its tools is also the model that produced the single hardest-to-explain correct answer, twice. I don't think that's a coincidence I can resolve from log data. It might just be a coincidence, full stop — a real file path is a small enough space that a lucky guess isn't impossible. But "lucky twice, in the exact same idiosyncratic way, in independent sessions" is exactly the kind of thing I'd want to look at with proper tracing before I either believed it or dismissed it.

What I learned

  • Fixing my methodology surfaced sharper findings, not messier ones. Running one model per process, instead of relaying through shared memory, didn't wash out the interesting behavior — it made the attribution cleaner. I now know these patterns belong to the model, not to context bleeding from whoever ran before it.
  • Tool restraint and tool coverage are two separate dials, and a model can have the wrong setting on either one independently. qwen2.5-coder:7b has restraint turned all the way up — to the point of never engaging its tools even when it should. llama3.2:3b has it turned down — reaching for a tool to answer 2 + 2. Neither setting is "smarter"; they're just miscalibrated in different directions.
  • A wrong answer and a broken answer are different failure classes, and they need different fixes. Granite4:micro's repetition loop and gemma4:12b's empty replies aren't reasoning mistakes — an agent built on top of these models needs a timeout and a retry policy regardless of which model is running, because this isn't a "pick a better model" problem.
  • Silent, confident guessing is worse than asking, but asking has a real cost too. I don't think either extreme I saw this round is the right default. qwen3:8b's refusal to guess a drive protected me from a wrong answer, but it also produced a "did nothing" turn on a request that was half-answerable. The models that guessed got more done and were occasionally wrong about it in ways I wouldn't have noticed without reading the tool trace myself.

Limitations

  • Five of six models this round, not six. qwen3-vl:8b-instruct didn't get a fresh-process run in this batch.
  • Two sessions needed a restart after a failure (granite4:micro's repetition loop, gemma4:12b's hang), which is itself informative but means I can't call every model's dataset "one uninterrupted run."
  • Small sample, still. Roughly 9-14 comparable turns per model. Enough to see a pattern repeat, not enough to put a percentage on anything.
  • Same hardware constraint as before — a laptop with no discrete GPU, running Q4_K_M quantized weights. Every timing number is a reflection of that machine, not a general claim about these models.
  • The qwen2.5-coder:7b file-path finding is reported, not solved. I ruled out my first-round explanation (shared context) with this round's fresh-process replication, but I don't have a replacement explanation yet.

What I want to test next

  1. Isolate whether qwen2.5-coder:7b supports native tool-calling through this integration at all — a minimal, single-tool, single-turn test outside the full agent, to see if it ever emits a real tool call under any circumstance.
  2. Capture full raw message traces, specifically for that model's file-path answers, to see if there's a code path I'm not accounting for.
  3. Add a timeout and retry layer to the agent itself, so a repetition-loop or empty-reply failure doesn't require me to manually cancel and restart the process.
  4. Re-run the "ask vs. guess" filesystem tasks with a rule that sits between the two extremes — try the most likely drive, but say so explicitly, instead of silently guessing or refusing to act at all.
  5. Repeat the exact same battery again, unchanged, to see how much of this round's specific pattern (which model stalls, which one over-searches) reproduces a third time versus varying run to run.
